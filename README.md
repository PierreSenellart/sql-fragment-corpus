# SQL Fragment Corpus

13,337 SQL queries from six existing sources. Each query comes with a PostgreSQL
instance to run it on and a label giving the SQL fragment it belongs to.

| source | scenarios | queries | |
|---|---:|---:|---|
| SEDE, the Stack Exchange Data Explorer | 7,804 | 7,804 | ships here |
| SQLShare, a hosted query service's log | 1,562 | 3,777 | by script |
| dba.stackexchange.com | 686 | 1,425 | ships here |
| BEAVER, an enterprise warehouse benchmark | 206 | 206 | ships here |
| TPC-DS | 99 | 103 | by script |
| TPC-H | 22 | 22 | by script |
| total | 10,379 | **13,337** | |

A *scenario* is a set of tables with their rows, and the queries that run on
them.

The corpus is all six sources. Three are included in this repository. The terms
of the other three do not permit redistribution, or do not clearly permit it, so
`scripts/` builds them from the originals (see below). The manifest and the
labels cover all six.

The corpus was built to test which fragment of SQL a provenance system supports.
It contains no test results.

## How the corpus was built

Four steps: extract the queries from each source, build an instance for each
scenario, check every query on PostgreSQL, and label the queries that pass.

| source | candidates | extracted (step 1) | included (step 3) |
|---|---:|---:|---:|
| SEDE | 12,023 | 9,052 | 7,804 |
| SQLShare | 11,121 | 5,083 | 3,777 |
| dba.stackexchange.com | 13,568 | 2,882 | 1,425 |
| BEAVER | 209 | 208 | 206 |
| TPC-DS | 103 | 103 | 103 |
| TPC-H | 22 | 22 | 22 |
| total | | 17,350 | **13,337** |

`candidates` is the number of queries in the source, except for
dba.stackexchange.com, where it is the number of distinct SELECT statements found
in the threads tagged `postgresql`, after the splitting and parsing described
below.

### Step 1: extract the queries

Each source was read as follows. Queries in T-SQL or MySQL were translated to
PostgreSQL with sqlglot; a query that cannot be translated faithfully is dropped
at this step.

**SEDE.** The `train`, `val` and `test` files of the SEDE dataset (see
`NOTICE.md`) hold 12,023 queries written on the Stack Exchange Data Explorer, in
T-SQL. Query parameters
(`##name##`) are replaced by their default value, or by a value of the declared
type. Then:

- 248 duplicates are dropped (same text up to whitespace);
- 2,556 are dropped because sqlglot does not parse them as a single T-SQL SELECT
  statement;
- 61 are dropped because the translation would silently lose part of them
  (`PIVOT`, `FOR XML`) or a parameter is left unfilled;
- 106 are dropped because they read no table, or a table that is not in the
  published SEDE schema.

9,052 queries remain, one scenario each.

**SQLShare.** `queries.txt` in Data Release 1 holds 11,121 queries, in T-SQL,
over datasets the users uploaded. Then:

- 1,845 duplicates are dropped;
- 1,388 are dropped because they name no dataset;
- 2,696 are dropped because they read a dataset that is not in the release
  (2,578) or that cannot be read from it (118);
- 109 are dropped because they cannot be translated into a single PostgreSQL
  SELECT statement.

5,083 queries remain, in 1,929 scenarios: one per set of datasets and views that
the queries read.

**dba.stackexchange.com.** The Stack Exchange Data Dump of 2024-04-02 (see
`NOTICE.md`) holds 17,389 question threads tagged `postgresql`. The code blocks
of each thread, question and answers in post order, are split into statements
and parsed with PostgreSQL's own parser; each distinct statement is kept once per
thread. This gives 13,568 SELECT
statements. Then:

- 59 are dropped because they hold a placeholder (`@x`, `$1`) instead of a value;
- 10,627 are dropped because their thread does not both create a table and insert
  rows into it, so there is nothing to run them on.

2,882 queries remain, in 1,027 scenarios, one per thread.

**BEAVER.** The `dev_dw.json` and `dev_nw.json` files of the `BEAVER-MAY-2025`
release (see `NOTICE.md`) hold 209 queries, in MySQL. One is dropped because it
holds a placeholder. 208 queries remain, one scenario each.

**TPC-DS.** The 99 query templates, generated by the kit's `dsqgen` as the
qualification queries:

    dsqgen -DIRECTORY query_templates -INPUT query_templates/templates.lst \
           -DIALECT netezza -QUALIFY Y -SCALE 1

Four templates hold two statements, which gives 103 queries in 99 scenarios.
None is dropped.

**TPC-H.** The 22 query templates, with fixed substitution values. None is
dropped.

The 17,350 extracted queries are the rows of `corpus/manifest.jsonl`.

### Step 2: build an instance for each scenario

- **SEDE, BEAVER, TPC-DS, TPC-H:** the rows are generated. The tables are those
  the query reads, with the source's schema: the published SEDE schema, the table
  definitions in the BEAVER release, the DDL of the TPC specifications. Each
  table gets 2 to 16 rows, fewer when a query reads many tables. Values come from
  small domains extended with the query's own constants, so that its conditions
  select something, and key columns share a small range of values, so that its
  joins match. Primary keys are respected: those the BEAVER release and the TPC
  DDL declare and, for SEDE, whose schema file declares none, the `Id` of every
  table and `(postid, tagid)` for `posttags`, as Stack Exchange's schema
  documentation gives them.
- **SQLShare:** the rows are sampled from the uploaded files in the release, 30
  rows from the first 2,000 lines of each file, with column types inferred from
  the values. The views are those of the release's `view_script.txt`.
- **dba.stackexchange.com:** the setup is the thread's own `CREATE`, `INSERT`,
  `ALTER` and similar statements, in post order. In 388 of the 1,027 scenarios
  (238 of the 686 included) these statements do not simply list the rows: they
  generate them (`INSERT ... SELECT`, `generate_series`, `CREATE TABLE AS`), some
  of them fail on PostgreSQL, or a table has more than 30 rows. There, the setup
  was replayed and the resulting instance written out as literal rows, each table
  sampled down to 30 rows. The field `materialised` says why, and `recipe` keeps
  the author's statements.

The text of setups and queries was then changed as the next section lists.

### Step 3: check every query on PostgreSQL

Each extracted query was run on a stock PostgreSQL 18.6, with no extension, over
its instance. It was then run again with the rows of every table stored in the
opposite physical order, and the two answers were compared as multisets. The
query and its setup were also checked for statements and functions whose result
does not depend on the data alone. A query is excluded for the following
reasons:

| reason | queries |
|---|---:|
| `does not run: query failed` | 2,348 |
| `does not run: setup failed` | 1,004 |
| `answer depends on the physical row order` | 335 |
| `reads no relation of the scenario` | 121 |
| `reads or changes server state` | 69 |
| `calls a volatile function` | 30 |
| `the setup calls a volatile function` | 30 |
| `modifies data` | 29 |
| `reads physical storage, not data` | 24 |
| `the query plan reads no relation: a condition is constant` | 22 |
| `a column's type is a table's row type, which the measurement could not compare` | 1 |

4,013 queries are excluded and 13,337 remain. An excluded query has one reason:
the first check it fails.

A query calling `random()`, `nextval()` or a uuid generator has no determined
answer. The same applies to 12 DBA.SE scenarios whose setup generates rows with
`random()` or `gen_random_uuid()`, since each replay builds different data: their
30 queries are excluded with the reason `the setup calls a volatile function`. 27
of them, in nine scenarios, would otherwise be included; the other three are
excluded for another reason as well. Two calls are allowed in a setup:
`nextval()` on a sequence the setup creates, which gives the same values on every
replay into an empty database, and a clock read, which is replaced by a fixed
moment.

All reasons but the last are properties of the query or its scenario. The last is
a limitation of the test the corpus was built for.

### Step 4: label the included queries

Each of the 13,337 included queries is labelled with the smallest fragment that
contains it; see Fragment labels below.

## Changes from the source text

The setups and queries in this repository are the text that ProvSQL is tested
on, which is not exactly the text of the sources. Apart from the translation by
sqlglot, it differs from the sources in the ways listed below. All these changes
were made before step 3, so the checks of step 3 tested this text.

**Renderings for PostgreSQL.** Some constructs sqlglot passes through unchanged
have no PostgreSQL equivalent under the same name, and are rewritten into one
that PostgreSQL accepts. A rewrite that would change which rows a query selects
is not made; such a query fails at step 3 instead.

- SEDE and SQLShare: the rules in `scripts/support/tsql_renderings.py`. These
  are exact for `PATINDEX` on a `'%X%'` pattern, `DATEFROMPARTS`, `VAR`, `VARP`,
  `+` next to a string literal, T-SQL's datetime zero (`0 + INTERVAL ...`, which
  is 1900-01-01) and the argument types of `make_timestamp`. Three are not exact:
  `STR(x)` does not pad its result to T-SQL's width of 10, and `round(x, n)` and
  `NUMBER_TO_STR` round the decimal value of a floating-point argument, not the
  binary one, which can differ on a value halfway between two roundings. A
  SQLShare scenario lists the rules it needed in `rendered`. SEDE query
  parameters are filled as described in step 1.
- BEAVER: the field `dialect` says what was done where the translation from MySQL
  needed more than sqlglot's default.
- TPC-DS: in 18 templates an interval written `+ N days` becomes
  `+ interval 'N days'` (field `dialect`).
- TPC-H: in Q1, `interval '[DELTA]' day (3)` loses its precision, `(3)`, which
  PostgreSQL does not accept (field `dialect`).

**Changes to the query.** These change the text of the query, not only its
dialect:

- TPC-DS 36, 70 and 86: an output column name used inside an `ORDER BY`
  expression, which PostgreSQL cannot resolve there, is replaced by its defining
  expression (field `altered`, and `faithful` is false).
- TPC-H Q15: the view is named `revenue0`, as the specification's stream 0
  requires, and the closing `DROP VIEW` is left out (field `deviation`).
- 589 queries: a smaller `LIMIT`. The test needs a `LIMIT` to cut the answer,
  and on an instance of a few rows per table a source's `LIMIT 100` keeps every
  row. So where a query's own `LIMIT` is at least the number of rows it returns,
  and that number is 2 or more, the `LIMIT` is lowered to one less than that
  number. For 107 of these queries, the lower `LIMIT` cuts between rows that tie
  in the `ORDER BY`, so the answer depends on the physical row order and step 3
  excludes them. The other 482 are in the corpus: 449 SEDE, 18 SQLShare, 12
  TPC-DS and 3 DBA.SE. The scripts take the values for their sources from
  `scripts/limits.json`.

**`public.` is removed.** A schema-qualified name breaks replaying in a schema of
its own: a query reading `public.items` finds nothing if the setup created
`items` in `u`. 12 DBA.SE setups and 7 DBA.SE queries used `public.`; it is
removed.

**Clock reads are fixed.** A setup calling `now()`, `current_timestamp` or
`current_date` would build a different instance each day, and a query calling
them would give a different answer. Every such call is replaced by one fixed
moment, `2026-06-15 12:00:00+02`: in 29 DBA.SE setups (22 more contain the same
moment in generated rows) and in 499 queries. Those queries are marked
`reads_the_clock` in the manifest, since their text no longer shows it.
`scripts/support/pin_moment.py` makes the replacement.

Labels were computed on the queries with the author's `LIMIT`. Classifying them
again with the reduced `LIMIT` gives the same label for every query. A clock
read is classified as a constant, so pinning it does not change a label either.

## Fragment labels

`labels/fragments.jsonl` has one row per query: `scenario`, `qid`, `fragment` and
`fragment_name`. The fragments form a chain: each contains all the ones before
it. A query is labelled with the smallest fragment that contains it. `outside`
means the query uses something no fragment covers.

`within` counts the queries a fragment contains, its own and those of every
smaller one.

| label | name | queries | | within |
|---|---|---:|---:|---:|
| F0 | `select-project-join-union` | 3,610 | 27.1 % | 3,610 |
| F1 | `relational-algebra` | 389 | 2.9 % | 3,999 |
| F2 | `expressions-over-values` | 1,477 | 11.1 % | 5,476 |
| F3 | `aggregation` | 2,354 | 17.7 % | 7,830 |
| F4 | `conditions-on-aggregates` | 436 | 3.3 % | 8,266 |
| F5 | `core-sql` | 2,036 | 15.3 % | 10,302 |
| F6 | `ordered-sql` | 1,469 | 11.0 % | 11,771 |
| F7 | `aggregate-values-as-data` | 1,239 | 9.3 % | 13,010 |
| F8 | `recursion` | 58 | 0.4 % | 13,068 |
| | `outside-the-levels` | 269 | 2.0 % | |

These proportions describe this corpus. They are not claimed to hold for SQL
beyond these six sources.

All 13,337 queries are labelled, including the 3,902 that are built by script.
`labels/vocabulary.json` describes each fragment in a paragraph.

## Files

### Scenario files

`corpus/<source>_scenarios.jsonl` has one JSON object per line:

```
id                  the scenario's identifier, "<source>/<name>"
setup               the statements to replay, in order. Mostly CREATE TABLE and
                    INSERT with literal rows; DBA.SE scenarios also create
                    indexes, views, materialized views, enum and domain types,
                    sequences, and ALTER TABLE
queries             [[qid, sql], ...]; (id, qid) is the key everything joins on
original            the query as its author wrote it, before translation (SEDE,
                    BEAVER)
dialect             BEAVER only: what the translation from MySQL did, where it
                    needed more than sqlglot's default
question            BEAVER's natural-language question for the query
recipe              DBA.SE only, on the 238 scenarios that have `materialised`:
                    the setup as extracted from the thread, before it was
                    replayed and rewritten as `setup`. A list of the authors'
                    statements, in post order; some of them may not run on
                    PostgreSQL (see `materialised`)
materialised        DBA.SE only: a STRING saying why the setup differs from the
                    author's. 238 scenarios have one:
                    "the setup has N statement(s) that do not run" (110, N from
                    1 to 21): some of the author's statements fail on
                    PostgreSQL, and the instance is what the others build;
                    "a table was sampled down" (59); "INSERT ... SELECT" (47);
                    "CREATE TABLE AS" (12); "a generated data source" (10).
                    In all but the first, the author's rows were replaced by
                    sampled or generated rows
```

To run a scenario, create a schema named `u` in an empty PostgreSQL database, set
`search_path = u, public`, replay `setup`, then run the queries. The schema must
be named `u`: 52 DBA.SE setups refer to their tables as `u.<table>`. Everything
was checked on PostgreSQL 18.6, and no extension is needed.

Queries are in PostgreSQL's dialect. SEDE queries were written in T-SQL and
BEAVER queries in MySQL; both were translated with sqlglot, and `original` keeps
the author's text. `dialect` records what was done for the BEAVER queries that
needed more than sqlglot's default translation.

Replaying a setup twice gives the same instance. This was checked on the files
of this repository: all 8,696 scenarios were replayed twice into a fresh schema,
the rows of every table compared, and all 9,435 queries run on the result. Every
instance was identical, every setup statement ran, and every query ran.

### Script output

The three scripts write the same fields, with these additions, which say how an
entry's text differs from the source:

```
original            TPC-DS, TPC-H: the statements as the kit gives them, before
                    the changes above (for TPC-H with the substitution values
                    filled in; for Q15, from CREATE VIEW to DROP VIEW)
originals           SQLShare: {qid: the query's T-SQL text}
rendered            SQLShare: the T-SQL renderings the scenario needed
dialect             TPC-DS, TPC-H: a rendering made for PostgreSQL
altered             TPC-DS: a change to the query text itself
deviation           TPC-H: a difference from the template that is not in the
                    query (Q15's view name and its DROP VIEW)
faithful            TPC-DS, TPC-H: false when the query text was altered
```

### The manifest

`corpus/manifest.jsonl` has one row for each of the 17,350 queries extracted in
step 1: 13,337 included and 4,013 excluded. For a source built by script, a row
has no `sql`, `original` or `error`, because an error message quotes the
source's tables and columns; `text_from` names the script instead.

Each row has `corpus`, `scenario`, `qid` and `included`, and may also have:
`sql` and `original`, as above; `rows`, the number of rows an included query
returns on its instance; `reads_the_clock`, described above; `reason`; and
`error`, the PostgreSQL message
as returned.

## Building the other three sources

The SQLShare query log (3,777 queries), TPC-DS (103) and TPC-H (22) are part of
the corpus but not included here: their terms do not permit redistribution, or
do not clearly permit it. `NOTICE.md` gives the details. The scripts build their
queries and instances from the originals, in the same format as the files in
`corpus/`, so the output joins the manifest and the labels on
`(scenario, qid)`. Unlike the files in `corpus/`, the output also contains
excluded queries; the manifest says which.

Each script was run on the originals and its output compared with the corpus:
all three reproduce it, scenario for scenario and query for query.

### SQLShare

    python3 scripts/sqlshare_extract.py sqlshare_scenarios.jsonl \
            --zip sqlshare_data_release1.zip

The script writes 1,929 scenarios; 1,562 of them hold a query in the corpus.

Data Release 1 is a single 3.6 GB zip. The script reads only a few hundred
kilobytes of it, without unpacking: `queries.txt`, `view_script.txt`, and the
first rows of each table a query reads. `--download` fetches the archive if it
is not already there. Its authors ask that four publications be cited; they are
listed in `NOTICE.md`.

### TPC-DS

    python3 scripts/tpcds_extract.py tpcds_scenarios.jsonl \
            --schema <kit>/tools/tpcds.sql --queries <dsqgen output dir>

Download the TPC-DS Tools from `https://www.tpc.org/`. Generate the queries with
the `dsqgen` command given in step 1; it writes one file per template. Point
`--queries` at the directory holding them, named `<n>.sql`. Four templates hold
two statements each, which gives 103 queries from 99 templates.

### TPC-H

    python3 scripts/tpch_extract.py tpch_scenarios.jsonl --kit <kit>/dbgen

Download the TPC-H Tools from `https://www.tpc.org/`. `--kit` is the `dbgen`
directory of the download, which holds `dss.ddl` and the 22 query templates in
`queries/<n>.sql`. The substitution values used for this corpus are in
`values.json` and `slotmap.json` next to the script, so `qgen` is not needed and
every run produces the same queries.

### Requirements

Python 3.10 or later. `scripts/requirements.txt` pins two parsers:

    pip install -r scripts/requirements.txt

The SQLShare script uses them to translate T-SQL and to check each statement
against the PostgreSQL grammar; `scripts/support/pin_moment.py` also uses them.
The two TPC scripts use only the standard library. The versions are pinned
because another version may translate or reject a query differently.

Helper modules shared by the scripts are in `scripts/support/`.
